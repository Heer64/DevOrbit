\section{Why this test}
Roles are the base of DevOrbit's permissions: Owner, Admin, Contributor and Viewer (\path{frontend/src/roles.js}, mirrored by
\path{backend/src/lib/permissions.js}). The backend tests already check that the API answers 403. No end-to-end test, however, checked what each
role actually sees and can do in the browser, nor that a role change made by the Owner takes effect for the other person.
That gap was in the tester's area (Sprint 1 roles, Sprint 2 tasks).

\section{The test}
One Playwright test (\path{e2e/tests/role-permissions.spec.js}, 78 lines) with two browser contexts, so there are two logged-in users at the same time:
\begin{enumerate}
\item \textbf{Setup:} the Member signs up. The Owner signs up and creates a Private project with the Member as a \textbf{Viewer},
      using the create form's \emph{Starting members} (US-08). The Owner's \emph{Team \& roles} shows the role menu for the Member set to Viewer.
\item \textbf{Viewer:} opens the project by URL. Checked: ``You: Viewer''; the message ``You are a Viewer on this project, so tasks are read-only.'';
      no \emph{Add task} button; ``Only Owners and Admins can change roles.''; no \emph{Role for \ldots} menus.
\item \textbf{Role change:} the Owner selects \emph{Contributor} (US-09) and sees ``\ldots{} is now Contributor.'' After a reload, the menu still says Contributor (saved).
\item \textbf{Contributor:} after a reload, ``You: Contributor'', the read-only message is gone, and they add a task, which appears in their list.
      The Owner reloads and sees the same task, so it was saved through the API.
\item \textbf{Contributor still cannot change roles:} no \emph{Role for \ldots} menus at all, including none for the Owner.
\end{enumerate}
Selectors use roles, labels and visible text, the same way the existing specs and the shared helpers (\texttt{signUp}, \texttt{addTask}, \texttt{taskRow}) do.

\section{Finding F2: flaky \texttt{DecisionsPanel.highlight} test}
\begin{checkinfo}
Where & \path{frontend/src/components/DecisionsPanel.highlight.test.jsx} (Sprint 6 M4, US-42; outside this tester's sprints). \\
Symptom & Fails at random on CI (here Node 20 only, while Node 22 passed on the same code); passes on re-run. \\
Cause & \path{DecisionsPanel.jsx} calls \texttt{scrollIntoView} in a \texttt{useEffect} (lines 116--121), which React runs after the rows are drawn.
The test checked the scroll once, right after \texttt{findByText('Deploy on Render')}. On a slow runner the check ran before the effect: a race. \\
Impact & Random red CI on unrelated pull requests, and the E2E job is skipped for that run. \\
Fix & Wait for the effect: \texttt{await waitFor(() => expect(scrolled).toEqual(['d2']))}. Test-only, two lines, in a separate PR (branch \texttt{fix/flaky-decisions-highlight-test}). \\
\end{checkinfo}

\section{Conclusion}
The new end-to-end test proves, through the real UI and API with two users, that a Viewer is read-only, that an Owner's role change takes
effect for the other user, and that a Contributor can add tasks but cannot change roles. It passes locally, in the full suite and in CI, and the
mutation check shows it fails when the permission rule is broken. Along the way, CI exposed a flaky frontend test from Sprint 6 (F2); its cause
was found and a fix prepared.
